Kroki treningu

Każdy krok treningu wskazuje dokładnie jeden typ aktywności: drill robota, ćwiczenie fizyczne albo serwis. Model TrainingStep wymaga dokładnie jednego pola referencyjnego z grupy drill_id, exercise_id, serve_id.

PoleTyp krokuZnaczenie
drill_idRobotID drilla z biblioteki drills_default.json. Runner pobiera aktualną nazwę i parametry piłek runtime.
exercise_idFizyczneID ćwiczenia z exercises_default.json. Używane w rozgrzewkach, cooldownach i programie 30-dniowym.
serve_idSerwisID serwisu z serves_default.json. Aktualnie brak w defaultowych treningach.
countRobotLiczba piłek do wyrzucenia w kroku. Zakres modelu: 1-999.
percentRobotTempo/prędkość względem bazowych parametrów drilla. Zakres modelu: 50-150.
duration_secĆwiczenie/serwisCzas trwania kroku. Dla ćwiczenia może nadpisać czas domyślny ćwiczenia.
pause_after_secWszystkiePrzerwa po kroku. Jeśli kolejny krok jest drillem, runner wykorzystuje końcówkę przerwy na rozkręcenie głowicy.
countdown_secTreningOdliczanie przed startem całego treningu.

Jak trening działa runtime

  • Ładowanie: training.get_trainings() skleja treningi domyślne i treningi użytkownika, a potem uzupełnia nazwy kroków przez aktualne biblioteki drilli, ćwiczeń i serwisów.
  • Readonly: treningi z JSON-a dostają readonly=true. Nie można ich edytować ani usuwać przez API. Można je duplikować.
  • Start: WebSocket akcja run_training pobiera trening po ID i przekazuje go do TrainingRunner.start().
  • Countdown: przed pierwszym krokiem runner odtwarza dźwięk startu, czeka 2 s, wysyła stan training_info i odlicza countdown_sec.
  • Preload głowicy: jeśli pierwszy albo następny krok jest drillem, runner potrafi rozkręcić głowicę przed właściwym startem, żeby ograniczyć martwy czas.
  • Krok drill: pobiera parametry balls z aktualnego drilla, uruchamia robot.run_drill(..., repeat=0, count, percent) i liczy postęp po eventach z robota.
  • Krok exercise: nie steruje robotem, tylko odlicza duration_sec, wysyła progres i opis ćwiczenia do UI.
  • Krok serve: jest obsługiwany w kodzie jako tryb timer albo response, ale obecne treningi defaultowe nie mają takich kroków.
  • Pauza po kroku: pause_after_sec generuje fazę przerwy. W ostatnich 3 sekundach runner daje sygnały dźwiękowe.
  • Skip warmup/cooldown: opcje UI pomijają początkowy lub końcowy blok ćwiczeń fizycznych. Indeksy pominiętych kroków trafiają do historii.
  • Historia: start tworzy wpis training_history ze statusem running, a koniec aktualizuje go na completed, stopped albo error.

API i edycja

EndpointZnaczenie
GET /api/trainingsZwraca treningi domyślne plus treningi użytkownika. Nazwy kroków są uzupełniane runtime.
GET /api/trainings/{id}Zwraca jeden trening albo 404.
POST /api/trainingsTworzy trening użytkownika w SQLite.
PUT /api/trainings/{id}Aktualizuje trening użytkownika. Dla readonly zwraca 403.
DELETE /api/trainings/{id}Usuwa trening użytkownika. Dla readonly zwraca 403.
POST /api/trainings/{id}/duplicateTworzy edytowalną kopię dowolnego treningu, także readonly.
Uwaga implementacyjna: endpointy REST przyjmują body: dict, więc pełna walidacja Pydantic z TrainingScenarioIn nie jest obecnie wymuszana na wejściu REST. Frontend wysyła poprawny kształt danych, ale przy automatycznych importach warto walidować JSON osobnym skryptem.
